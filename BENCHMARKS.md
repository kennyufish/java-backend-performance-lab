# Benchmark Report

This report consolidates the two performance experiments implemented by Java Backend Performance Lab. Every result below was generated by this repository and can be traced to committed machine-readable or raw evidence.

## Executive summary

| Experiment | Baseline | Optimized | Observed ratio |
| --- | ---: | ---: | ---: |
| Authentication mean response time | 34 ms | 6 ms | **5.667x ratio** |
| Authentication p95 response time | 37 ms | 14 ms | **2.643x ratio** |
| PostgreSQL median query time | 53.489 ms | 0.040 ms | **1337.225x ratio** |

The authentication experiment shows the latency avoided when an active session can be reused instead of repeating documented synthetic upstream work. The database experiment shows the plan change produced by an index aligned with the query's filters and ordering.

These results describe the exact local methods below. They do not establish production throughput, capacity, or expected performance on another system.

## Experiment 1: authentication session reuse

### Question

How does reusing an active session affect API latency when creating a new session includes a fixed, synthetic representation of upstream authentication work?

### Compared paths

- `POST /api/v1/auth/baseline` creates a new UUID-backed session for every request.
- `POST /api/v1/auth/session-reuse` uses a thread-safe in-memory store and reuses the session for the same `clientId` while its TTL remains active.

The `load-test` profile adds a `20ms` delay only when a new session is created. Normal application runs default this delay to zero. The delay is an explicit experimental input, not a measurement of an employer system or a real identity provider.

### Workload

| Parameter | Value |
| --- | ---: |
| Request rate | 100 new users per second |
| Client pool | 100 deterministic client IDs |
| Warm-up | 5 seconds per case |
| Measurement | 15 seconds per case |
| Measured requests | 1,500 per case |
| Synthetic new-session delay | 20 ms |

Gatling runs the two cases sequentially with the same application process, HTTP stack, request rate, and client distribution. Warm-up requests have a separate request name and are excluded from the measured rows. Reuse warm-up populates all 100 client sessions before measurement.

Assertions require HTTP 200, the correct `reused` field, zero failed measured requests, and measured p95 below 1,000 ms.

### Result

| Metric | Authenticate every request | Reuse active session | Comparison |
| --- | ---: | ---: | ---: |
| Requests | 1,500 | 1,500 | equal |
| Failures | 0 | 0 | equal |
| Minimum | 24 ms | 3 ms | — |
| p50 | 33 ms | 5 ms | — |
| Mean | 34 ms | 6 ms | **5.667x ratio** |
| p95 | 37 ms | 14 ms | **2.643x ratio** |
| p99 | 51 ms | 31 ms | — |
| Maximum | 65 ms | 66 ms | — |

The mean result reflects the expected mechanism: the measured reuse path avoids the synthetic new-session delay after warm-up. The overlapping maximum values also show why the report includes percentiles and does not characterize the system using one best or worst request.

### Reproduce

```powershell
$env:LAB_DB_PASSWORD = '<your-local-lab-password>'
.\scripts\run-auth-load-test.ps1
```

The script packages and starts the application with the `load-test` profile, waits for health, runs both Gatling cases, copies the raw logs, writes the JSON summary, and stops the application.

## Experiment 2: PostgreSQL composite index

### Question

How does a composite index aligned with the filter and sort pattern change the execution plan and latency of a recent-event lookup over a deterministic large dataset?

### Query

```sql
SELECT id, tenant_id, customer_id, event_type, occurred_at, payload
FROM customer_events
WHERE tenant_id = 42
  AND event_type = 'PURCHASE'
  AND occurred_at >= TIMESTAMPTZ '2025-01-01 00:00:00+00'
ORDER BY occurred_at DESC
LIMIT 100;
```

The matching Flyway migration creates:

```sql
CREATE INDEX idx_customer_events_tenant_type_occurred_at
    ON customer_events (tenant_id, event_type, occurred_at DESC);
```

The equality filters lead the index, followed by the time range and descending order used to return the newest matching events.

### Method

| Parameter | Value |
| --- | ---: |
| Dataset | 1,000,000 deterministic rows |
| Dataset generator | PostgreSQL `generate_series` |
| Data load time | 3,405 ms |
| Warm-up runs | 2 per case |
| Measured runs | 5 per case |
| Returned rows | 100 |
| Measurement | `EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)` |

The runner removes the lookup index for the baseline, measures the query, restores the index in a `finally` block, and repeats the measurement. The committed JSON contains all execution times and representative plans.

### Result

| Case | Plan | Execution times | Median |
| --- | --- | --- | ---: |
| Before index | Sequential scan | 50.956, 55.910, 52.426, 53.489, 54.409 ms | 53.489 ms |
| After index | Index scan | 0.045, 0.045, 0.039, 0.040, 0.037 ms | 0.040 ms |

Observed median ratio: **1337.225x** for this exact query, generated dataset, warm-cache method, and local machine.

The representative plan changes from `Seq Scan` with no lookup index to `Index Scan` using `idx_customer_events_tenant_type_occurred_at`. This is a query-plan result, not a claim that every database query or production workload improves by the same ratio.

### Reproduce

The runner replaces the contents of `customer_events`. Use only an isolated lab database.

```powershell

.\scripts\run-benchmark.ps1 -Rows 1000000
```

## Independent verification

The repository provides three verification layers:

1. `mvnw clean verify` runs six HTTP integration tests against PostgreSQL and packages the application.
2. Docker Compose builds a multi-stage, non-root Java image, waits for PostgreSQL and Spring Boot health checks, and exposes the application health endpoint.
3. GitHub Actions repeats the integration suite and Compose health verification on a fresh Ubuntu runner.

## Limitations

- Both reports contain one paired run on one local machine.
- The authentication experiment uses a documented synthetic delay and no real credential provider.
- Authentication cases run sequentially, not simultaneously, and the reuse store is pre-warmed.
- Session state is process-local and does not model a distributed session store.
- The database experiment uses warm-up runs and a deterministic data distribution.
- Cache state, storage, CPU, JVM state, PostgreSQL settings, concurrency, query shape, and data distribution can materially change results.
- Neither experiment is a saturation test or a production-capacity claim.
